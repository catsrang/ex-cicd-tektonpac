## Implementation
End-to-end flow as designed by the guide:

1. **Trigger**: a developer pushes a branch / opens a PR, or pushes directly to `main`, on the GitHub `app-repo` (this repository once populated).
2. **Event delivery**: the installed GitHub App sends a webhook to the PAC controller/webhook/watcher running on the target cluster (in namespace `pipelines-as-code` on vanilla Kubernetes, `openshift-pipelines` on OpenShift).
3. **Matching**: PAC looks up the `Repository` CRD matching the repo URL to determine the target namespace, then matches `.tekton/*.yaml` files by their `pipelinesascode.tekton.dev/on-event` and `on-target-branch` annotations (`pull_request` vs `push`, target `main`).
4. **Resolution**: PAC resolves every `Task` referenced via the `pipelinesascode.tekton.dev/task` (and `task-1`, …) annotations — Tekton Hub tasks (`git-clone`, `maven`, `buildah`) plus the in-repo custom Task (`update-deployment-tag.yaml`, resolved by relative path) — and inlines them into one self-contained `PipelineRun`, applied to the cluster in the Repository CR's namespace.
5. **PR pipeline execution** (`.tekton/pr.yaml`): `git-clone` → `maven test` → `buildah` build of a throwaway PR-tagged image (`demo-app:pr-{{ pull_request_number }}`); no push, no deployment-repo write. Status is reported back to GitHub's Checks tab per task, with a PR comment on parse errors.
6. **Push pipeline execution** (`.tekton/push.yaml`, on merge to `main`): `git-clone` → `maven package` → `buildah` build **and push** the real image tagged with the commit SHA (`{{ revision }}`) → `update-deployment-tag` custom Task authenticates with the PAC-managed short-lived `{{ git_auth_secret }}` (GitHub App installation token, ~8h TTL) to clone `deployment-repo`, `yq`-patch `charts/demo-app/values.yaml`'s `image.tag`, commit, and push to `deployment-repo`'s `main`.
7. **Downstream deployment**: if ArgoCD/Flux watches `deployment-repo` (assumed, per the existing project pattern this guide extends), the tag bump drives an automatic deployment — outside this repo's scope.
8. **Feedback/GitOps loop**: PR authors can comment `/retest`, `/test <name>`, or `/ok-to-test` to control re-runs; access to auto-triggered CI defaults to collaborators/org owners/`OWNERS` file, optionally narrowed via the Repository CR's `policy.pull_request` / `policy.ok_to_test` team lists.

Local pre-push validation is supported via `tkn pac resolve -f .tekton/pr.yaml -o /tmp/pr-resolved.yaml` followed by `kubectl create -f`, letting the resolved PipelineRun be tested against a dev cluster without a live GitHub event.

## Dependencies
**Internal** (none yet — repo is empty; these become internal once created)
- `.tekton/pr.yaml` / `.tekton/push.yaml` — depend on `.tekton/tasks/update-deployment-tag.yaml` being present at the same commit SHA (PAC resolves same-repo Tasks by relative path, keeping Task and Pipeline changes atomic).

**External**
- **Pipelines as Code (PAC) controller** — must be installed on the target cluster (OpenShift Pipelines Operator ≥1.7.x, or `pipelines-as-code/stable/release.k8s.yaml` on vanilla Kubernetes) before any event from this repo can be processed.
- **GitHub App** — must be created (via `tkn pac bootstrap` or manually) and installed on this repo (and on `deployment-repo` if token scoping isn't widened) before PR/push events reach the cluster.
- **Tekton Hub Tasks**: `git-clone`, `maven`, `buildah` — resolved at run time from Tekton Hub (or whatever catalog the cluster's PAC is configured against); not vendored into this repo.
- **`yq`, `git`** (inside the `update-deployment-tag` Task's `ubi9/ubi-minimal` step image) — installed at runtime via `microdnf install`.
- **`tkn` / `tkn-pac` CLI** — used for `bootstrap`, `create repository`, `resolve`, `logs`, `describe`; a dev/operator tool, not a repo dependency.

## Constraints & Edge Cases
- The guide's exact Task parameter names (`GOALS`, `IMAGE`, etc.) are flagged by its own author as unverified against a live Tekton Hub fetch — they should be diffed against whatever Hub/catalog version actually resolves on the target cluster before being trusted verbatim.
- `pipelinerun_provenance: "default_branch"` (recommended in the Repository CR) resolves `.tekton/` from `main` rather than the PR head, specifically to prevent a malicious fork PR from shipping its own pipeline definition — an important security default, not optional hardening.
- The GitHub App's installation token (`{{ git_auth_secret }}`) is scoped only to the triggering repo by default; writing to `deployment-repo` requires explicitly listing it under `github_app_token_scope_repos` on the Repository CR, or the push pipeline's final step fails with a 403.
- PAC always runs PipelineRuns in the namespace where the matching `Repository` CR lives — this repo's `.tekton/` files carry no namespace information themselves.
- First-time/external contributors' PRs do not auto-trigger CI; a maintainer must comment `/ok-to-test` (unless covered by an `OWNERS` file or a `policy.pull_request` team).
- No PAT/long-lived secret is used for GitHub auth (a deliberate improvement over the project's older Triggers-based guides) — all Git write access flows through the ~8-hour GitHub App installation token.
