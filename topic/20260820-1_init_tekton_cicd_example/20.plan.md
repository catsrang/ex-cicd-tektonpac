# Implementation Plan: Init Tekton PAC CI/CD Example Project

## Executive Summary
Bootstrap `ex-cicd-tektonpac` as a self-contained Pipelines-as-Code (PAC) example: this repo becomes the guide's `app-repo` (Spring Boot Java app + `.tekton/` pipelines together), targeting a vanilla Kubernetes/k3s cluster, with a companion `deployment-repo` created to receive GitOps image-tag bumps on merge to `main`.

## Goals & Objectives
- [ ] Primary: PAC controller installed and reachable from GitHub on a vanilla Kubernetes cluster.
- [ ] Primary: GitHub App created, installed on both `app-repo` (this repo) and `deployment-repo`, with cluster secret provisioned.
- [ ] Primary: `app-repo` populated with a minimal Spring Boot app, Dockerfile, and `.tekton/pr.yaml` + `.tekton/push.yaml` pipelines matching the guide.
- [ ] Primary: `deployment-repo` created with a minimal Helm chart (`charts/demo-app/values.yaml`) as the GitOps target.
- [ ] Secondary: Local resolve/validation of pipelines before first real GitHub event.
- [ ] Secondary: End-to-end proof — PR triggers Checks-tab feedback; merge to `main` builds, pushes an image, and bumps `deployment-repo`'s tag.

## Phase-by-Phase Plan

### Phase 1 — Cluster Installation (Vanilla Kubernetes)
Install the PAC controller/webhook/watcher on the target cluster and confirm it's reachable from the public internet (directly or via `gosmee`).
- Apply the stable PAC release manifest; verify `controller`, `webhook`, `watcher` deployments are `1/1`.
- Decide and configure the webhook delivery path: real Ingress (needs a domain/TLS) vs. `gosmee` forwarder against `hook.pipelinesascode.com` (no public endpoint required, good for a local/demo cluster).
- **Exit criteria**: a webhook POST from GitHub can reach the PAC controller (verified with a placeholder/test event or during Phase 2's App creation flow).

### Phase 2 — GitHub App & Cluster Secret
Create the GitHub App that authenticates PAC to GitHub, and provision the cluster secret it reads from.
- Run `tkn pac bootstrap` (covers install-if-missing, App creation, and secret generation in one flow) — or fall back to the manual App-creation steps if bootstrap can't detect the cluster endpoint.
- Confirm App permissions/events match the guide (Checks, Contents, Issues, PRs read/write; Push/PR/Check events subscribed).
- Create `pipelines-as-code-secret` in the `pipelines-as-code` namespace from the App's ID, private key, and webhook secret.
- Install the App on **both** this repo and the (not-yet-created) `deployment-repo` — revisit this step after Phase 4 if `deployment-repo` doesn't exist yet.
- **Exit criteria**: secret exists in-cluster; App shows as installed on at least this repo.

### Phase 3 — `deployment-repo` Creation
Create the companion repository that receives GitOps tag bumps, since it was scoped in.
- Create a new GitHub repo (name/org to be decided) with a minimal Helm chart skeleton: `charts/demo-app/values.yaml` containing an `image.tag` field the push pipeline will patch.
- Install the GitHub App on this repo too (loops back to Phase 2's App-install step).
- **Exit criteria**: `deployment-repo` exists, has a `main` branch, and `charts/demo-app/values.yaml` with a placeholder `image.tag`.

### Phase 4 — Repository CRD Registration
Register this repo's URL with PAC so incoming events route to a namespace.
- Create the `Repository` CR (via `tkn pac create repository` or applied YAML) pointing at this repo's URL, targeting a chosen namespace (e.g. `cicd-demo`).
- Set `settings.pipelinerun_provenance: default_branch` (resolve `.tekton/` from `main`, not the PR head — security default from the guide).
- Set `settings.github_app_token_scope_repos` to include `deployment-repo`, so the push pipeline's installation token can write to it.
- **Exit criteria**: `tkn pac describe` shows the Repository CR resolved and pointed at the right namespace.

### Phase 5 — Java App Scaffolding (`app-repo` content)
Populate this repo with the minimal Spring Boot demo the pipelines will build.
- `pom.xml` (Maven, Spring Boot Maven plugin).
- `Dockerfile` (multi-stage UBI OpenJDK build, per the guide).
- `src/main/java/.../DemoApplication.java` and a minimal `src/test/java/.../DemoApplicationTests.java` (needed so the PR pipeline's `maven test` step has something to run).
- **Exit criteria**: app builds and tests pass locally with plain `mvn test` / `docker build`, independent of any pipeline.

### Phase 6 — PAC Pipeline Definitions
Author the `.tekton/` files that PAC will discover and run.
- `.tekton/pr.yaml`: `pull_request` → `main`; `git-clone` → `maven test` → `buildah` build of a throwaway PR-tagged image, no push.
- `.tekton/push.yaml`: `push` → `main`; `git-clone` → `maven package` → `buildah` build+push (SHA-tagged) → `update-deployment-tag`.
- `.tekton/tasks/update-deployment-tag.yaml`: custom Task that clones `deployment-repo` using the PAC-managed `{{ git_auth_secret }}`, patches `image.tag` with `yq`, commits, and pushes.
- Cross-check Task param names (`GOALS`, `IMAGE`, etc.) against whatever Tekton Hub/catalog version actually resolves on this cluster — the guide flags these as unverified.
- **Exit criteria**: all three files present and internally consistent (annotations reference the right Task names/paths).

### Phase 7 — Local Resolution & Dry Run
Validate the pipelines render correctly before relying on a live GitHub event.
- `tkn pac resolve -f .tekton/pr.yaml -o /tmp/pr-resolved.yaml`, inspect the rendered PipelineRun.
- Optionally `kubectl create -f` the resolved file against a dev namespace to confirm the Tasks actually execute (clone, test, build) outside of any GitHub trigger.
- **Exit criteria**: resolved PipelineRun applies and runs to completion (or fails for expected/understood reasons, e.g. missing registry creds) without a resolution-time error.

### Phase 8 — End-to-End Validation
Prove the full loop against real GitHub events.
- Push a branch, open a PR against `main`; confirm the Checks tab shows `app-repo-pull-request` with per-task status.
- Merge to `main`; confirm `app-repo-push-main` runs, pushes the image, and commits/pushes the tag bump to `deployment-repo`.
- Confirm `deployment-repo`'s `charts/demo-app/values.yaml` reflects the new `image.tag` after the run.
- Exercise GitOps commands (`/retest`, `/ok-to-test`) at least once to confirm they're wired up.
- **Exit criteria**: a full push-to-main cycle updates `deployment-repo` without manual intervention.

### Phase 9 — Access Control (optional hardening)
Only if the example should demonstrate restricted triggering, not just the default collaborator/OWNERS behavior.
- Add `settings.policy.pull_request` / `settings.policy.ok_to_test` team references to the Repository CR.
- **Exit criteria**: a non-listed external PR shows a pending check until an authorized `/ok-to-test` comment is made.
