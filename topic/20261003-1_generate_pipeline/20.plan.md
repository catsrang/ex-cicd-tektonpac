# Implementation Plan: Generate CI Pipeline (Task / Pipeline / PipelineRun) with In-Memory Build Workspace

## Executive Summary
Add three standalone Tekton resources under a new `tekton_ci/` folder — a custom Task that clones and Maven-builds on a 2Gi memory-backed workspace and copies only the jar (plus `Dockerfile`) to a PVC, a Pipeline that chains that Task to `buildah` over the shared PVC, and a PipelineRun that binds both workspaces. The Maven build stage is removed from `Dockerfile`, so the Tekton Task is the single build and the image is assembled from the pre-built jar.

## Goals & Objectives
- [ ] Primary: `Dockerfile` is runtime-only — no Maven stage, `COPY`s `target/demo-0.0.1-SNAPSHOT.jar` from the build context.
- [ ] Primary: `tekton_ci/task.yaml` — one Task (`clone-build-memory`): clone → `mvn package` on tmpfs → copy jar + `Dockerfile` to the PVC, in a single pod.
- [ ] Primary: `tekton_ci/pipeline.yaml` — a `Pipeline` wiring the custom Task → `buildah` (no push) over one shared PVC workspace.
- [ ] Primary: `tekton_ci/pipelinerun.yaml` — a `PipelineRun` with `pipelineRef`, binding `build-mem` (memory `emptyDir`, 2Gi) and `shared` (`volumeClaimTemplate`, 1Gi RWO).
- [ ] Primary: memory capped at 2G, proven on the cluster to be memory-backed and capped.
- [ ] Secondary: existing `.tekton/` pipelines keep passing after the `Dockerfile` change.
- [ ] Secondary: `CLAUDE.md` commands reflect the new build flow and `tekton_ci/`.

## Current State Assessment

### What Exists
- `.tekton/pr.yaml`: Hub `git-clone` → `maven` (`GOALS: ["test"]`) → `buildah` (`SKIP_PUSH`), on one 1Gi RWO `volumeClaimTemplate` (`source`).
- `.tekton/push.yaml`: same shape with `GOALS: ["package"]`, real push, then `update-deployment-tag`.
- `.tekton/tasks/update-deployment-tag.yaml`: the repo's custom-Task style (`tekton.dev/v1`, `script:` with `set -euo pipefail`, UBI image).
- `Dockerfile`: multi-stage; the build stage runs `mvn -B -DskipTests package`, the runtime stage copies the jar from it. Every image build compiles a second time.
- No `.dockerignore`; `target/` is git-ignored only.
- Cluster (per spec): Tekton Pipelines v1.16.0, `enable-api-fields: beta`, `coschedule: workspaces`, `local-path` StorageClass, no `LimitRange`/`ResourceQuota` in `cicd-demo`.

### What's Missing
- The `tekton_ci/` folder and all three resources.
- A custom Task replacing Hub `git-clone` + `maven` (they cannot share an `emptyDir` across pods).
- A runtime-only `Dockerfile` that consumes a pre-built jar.
- A jar on the workspace in `.tekton/pr.yaml` (`test` produces none) — it will fail at `build-image` once the Dockerfile stops building.
- A way to resolve `buildah` **outside PAC** (in `.tekton/` PAC inlines it from the Hub via annotation).
- Any memory limit or memory-backed volume anywhere in the repo.
- Validation commands for resources outside `.tekton/`.

### Decisions this plan assumes (spec open questions)

## Implementation Phases

### Phase 1 — Prepare `.tekton/pr.yaml` for a jar-consuming Dockerfile
**Goal:** make the existing PR pipeline leave a jar on its workspace, before the Dockerfile depends on one.

- Change `maven-test`'s `GOALS` from `["test"]` to `["package"]` (tests still run; the task name may stay or become `maven-package` as in `push.yaml`).
- `.tekton/push.yaml` needs no change — it already runs `package` before `buildah`.
- **Must be merged to `main` on its own, first.** With `pipelinerun_provenance: default_branch`, PAC takes `pr.yaml` from `main` but the `Dockerfile` from the PR head; if both changed in one PR, that PR would run the old `test` goal against the new Dockerfile and fail at `build-image`. The goal change is harmless with the current multi-stage Dockerfile, so it can land alone.

**Exit check:** a PR run on `main`'s new `pr.yaml` passes with the unchanged Dockerfile, and `target/demo-0.0.1-SNAPSHOT.jar` exists on the `source` workspace.

### Phase 2 — Runtime-only `Dockerfile`
**Goal:** the image build packages a pre-built jar and compiles nothing.

- Delete the `build` stage (`FROM …/openjdk-17 AS build` through `RUN mvn -B -DskipTests package`).
- Keep the runtime stage (`ubi9/openjdk-17-runtime`, `WORKDIR /deployments`, `EXPOSE 8080`, `ENTRYPOINT`); replace `COPY --from=build /build/target/…jar app.jar` with a `COPY` of `target/demo-0.0.1-SNAPSHOT.jar` from the build context.
- Do not add a `.dockerignore` that excludes `target/`.
- Local check: `mvn package` then `docker build -t demo-app .` succeeds and the container starts; `docker build` without a prior `mvn package` fails on the missing jar (expected, to be documented in Phase 7).

**Exit check:** local build + run OK; PR carrying this change passes `.tekton/pr.yaml` (now `package`); after merge, `.tekton/push.yaml` builds and pushes from the jar produced by its `maven-package` task.

### Phase 3 — Custom Task: `tekton_ci/task.yaml`
**Goal:** a self-contained Task that leaves exactly the image build context on the PVC.

- **Metadata/params**: `tekton.dev/v1` `Task` named `clone-build-memory`; params `repo_url`, `revision`.
- **Workspaces**: `build-mem` (clone + build; medium is the PipelineRun's concern) and `output` (PVC hand-off).
- **Step `clone`**: clone `repo_url` into `$(workspaces.build-mem.path)` and check out the exact `revision` SHA.
- **Step `build`**: `mvn -B package` in the memory workspace — the only Maven build in the flow, tests included.
  - `computeResources.limits.memory: 2Gi` (and a matching request) on this step.
  - Bound the JVM explicitly via `MAVEN_OPTS` (`-Xmx` well under 2Gi), since tmpfs pages are charged to the same limit.
  - Keep the Maven local repository off the tmpfs (container filesystem).
- **Step `copy`**: copy to `$(workspaces.output.path)`, preserving repo-relative paths:
  - `target/demo-0.0.1-SNAPSHOT.jar` — selected by exact name so the Spring Boot `.jar.original` is not picked up;
  - `Dockerfile`.

  Fail non-zero if the jar is missing or the copy fails, so `buildah` never starts on an incomplete context. Nothing else (source, `pom.xml`, `.git`) leaves the memory workspace.
- **UID consistency**: the git image and the UBI OpenJDK image have different default users; set one explicit `securityContext.runAsUser` for all three steps and leave the copied files readable by `buildah`.
- **Style**: `script:` blocks with `#!/usr/bin/env bash` + `set -euo pipefail`, matching `update-deployment-tag.yaml`.

**Exit check:** `kubectl apply --dry-run=server -f tekton_ci/task.yaml -n cicd-demo` passes.

### Phase 4 — Pipeline: `tekton_ci/pipeline.yaml`
**Goal:** a named `Pipeline` connecting the Task to the image build via the shared PVC.

- **Metadata/params**: `Pipeline` named `ex-cicd-tektonpac-ci`; params `repo_url`, `revision`, `image` (default `ghcr.io/catsrang/demo-app:ci`).
- **Workspaces**: `build-mem` and `shared`, declared once at Pipeline level.
- **Task `clone-build`**: `taskRef: clone-build-memory`; `build-mem → build-mem`, `output → shared`.
- **Task `build-image`**: `buildah`, `runAfter: [clone-build]`; `source → shared`; `IMAGE=$(params.image)`, `SKIP_PUSH=true`. Default `DOCKERFILE`/`CONTEXT` work because `Dockerfile` and `target/<jar>` sit at the PVC root at their repo-relative paths.
- **Resolving `buildah` without PAC** — pick one, in this order:
  1. `taskRef` with the **hub resolver**, version pinned to the one PAC currently pulls for `.tekton/pr.yaml`.
  2. If the resolver is not enabled or cannot reach the catalog: install the same pinned `buildah` Task into `cicd-demo` and reference it by name.

  Which one works on this cluster is not yet verified — check first, since it decides the YAML shape.

**Exit check:** server-side dry-run passes; the `buildah` reference resolves.

### Phase 5 — PipelineRun: `tekton_ci/pipelinerun.yaml`
**Goal:** a runnable binding of params and workspaces.

- `metadata.generateName` (used with `kubectl create`), namespace `cicd-demo`.
- `pipelineRef: ex-cicd-tektonpac-ci`.
- **Params**: concrete `repo_url` and `revision`, since PAC's `{{ … }}` placeholders are not substituted outside PAC. The header comment names the values to edit per run. The `revision` must be a commit that already contains the Phase 2 `Dockerfile`.
- **Workspaces**:
  - `build-mem` → `emptyDir: {medium: Memory, sizeLimit: 2Gi}`
  - `shared` → `volumeClaimTemplate`, `ReadWriteOnce`, `1Gi`.
- No `taskRunSpecs[].computeResources` (alpha; cluster is on `beta`) — the limit lives in the Task.

**Exit check:** server-side dry-run passes with Task and Pipeline applied.

### Phase 6 — Cluster validation
**Goal:** prove behaviour, not just schema.

1. **Happy path**: apply Task + Pipeline, create the PipelineRun, both TaskRuns succeed; `buildah` builds the image without pushing.
2. **Single build**: the `build-image` log shows no Maven execution and no dependency downloads — only base-image pull and the jar `COPY`.
3. **Memory-backed**: in the `clone-build` pod the `build-mem` mount is `tmpfs` sized 2Gi; the pod spec shows `medium: Memory` and the build step's 2Gi limit.
4. **Shared PVC, minimal content**: exactly one PVC for the run, mounted by both TaskRun pods; it contains only `Dockerfile` and `target/demo-0.0.1-SNAPSHOT.jar`.
5. **Peak usage**: record the build step's memory peak to confirm headroom under 2Gi with the chosen `-Xmx`.
6. **Failure paths**: a bad `revision` fails at `clone`; a failing test fails at `build`; in both cases `build-image` is not started.
7. **Existing pipelines**: a PR run (`.tekton/pr.yaml`) and a push run (`.tekton/push.yaml`) both pass with the runtime-only Dockerfile, and the pushed image starts.

Any fix found here goes back into the Phase 1–5 files.

### Phase 7 — Documentation
- `CLAUDE.md`:
  - Commands: drop "`Dockerfile` does this too"; state that `docker build` requires `mvn package` first.
  - Architecture / Key pieces: `pr.yaml` now runs `mvn package`; add `tekton_ci/` with its validation commands (`kubectl apply --dry-run=server`, apply Task/Pipeline, `kubectl create` PipelineRun) and the note that PAC does not read this folder.
- `README.md` / `tektonpac_impl_guide.md`: correct any statement that the image build compiles the app or that the PR pipeline runs only `mvn test`.
- Record in the topic's impl log the gotchas confirmed in Phase 6 (emptyDir not shared across tasks; tmpfs counted against the memory limit; `buildah` resolution outside PAC; provenance ordering of `pr.yaml` vs `Dockerfile`).

## Dependencies & Order
- **Phase 1 must reach `main` before Phase 2** (provenance ordering). They are separate merges.
- Phase 3 → 4 → 5 are sequential (each references the previous resource) and can be written in parallel with Phases 1–2, but can only be *validated* against a revision containing the Phase 2 `Dockerfile`.
- Phase 6 needs cluster access to `cicd-demo` and outbound access to the git host, Maven Central and the image registries.
- Phase 7 follows Phase 6's findings.

## Risks
- **Provenance ordering**: merging the Dockerfile change before (or together with) the `pr.yaml` goal change breaks PR runs at `build-image`, with the error one task away from its cause.
- **`buildah` resolution outside PAC** (Phase 4) — the only part with an unverified cluster dependency.
- **Memory budget**: tmpfs + JVM heap share the 2Gi limit; an unbounded heap or a Maven repo on tmpfs can OOM-kill the build step before `sizeLimit` triggers.
- **Per-step limits add up**: only the build step gets the 2Gi limit; 2Gi on all three steps would make the pod's total limit 6Gi.
- **Hard-coded jar name** in both the copy step and `Dockerfile`: a `pom.xml` version bump breaks both until updated (already true for the Dockerfile today).
- **UID mismatch between step images** — mitigated by a single `runAsUser`.

## Out of Scope
PAC-triggered entry point under `.tekton/` for `tekton_ci/`, image push and `update-deployment-tag` in the new pipeline, `pom.xml` or application changes, `infra/pac/` changes, dependency caching between runs.
