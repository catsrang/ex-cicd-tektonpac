# Generate CI Pipeline (Task / Pipeline / PipelineRun) with In-Memory Build Workspace

## Overview
The existing CI in this repo is expressed as two PAC `PipelineRun` files with inline `pipelineSpec` (`.tekton/pr.yaml`, `.tekton/push.yaml`) that chain Tekton Hub tasks (`git-clone` → `maven` → `buildah`) over a single 1Gi PVC workspace. This topic asks for a new, explicitly separated set of Tekton resources — a **Task**, a **Pipeline**, and a **PipelineRun** — for the CI work, written under a new **`tekton_ci/`** folder at the repo root, using `.tekton/` as the reference for conventions. The functional change versus the reference is the I/O model: `git clone` and the Maven build run on a **memory-backed workspace** (tmpfs `emptyDir`), and only the build result — **the jar** (plus the `Dockerfile` needed as build context) — is **copied to a PVC workspace** for the image build. Compilation happens **only in the Tekton Task**: the Maven build stage is removed from `Dockerfile`, which becomes a runtime-only image definition that packages the pre-built jar. The two workspaces have deliberately different scopes: the memory workspace is **task-local** (one pod), while the PVC workspace is the **only volume shared between tasks** and is the sole hand-off channel in the pipeline. Memory is capped at **2G**.

## Scope
- **In scope**
  - What the three new resources in `tekton_ci/` must contain and how they relate.
  - How the memory workspace → PVC hand-off has to be structured to work in Tekton.
  - What "memory limit = 2G" maps to in Tekton/Kubernetes terms.
  - How `tekton_ci/` interacts (or doesn't) with PAC, which only auto-discovers `.tekton/`.
  - Removing the Maven build stage from `Dockerfile` (runtime-only image from a pre-built jar), and what that does to the existing `.tekton/` pipelines and local `docker build`.

- **Out of scope**
  - Writing the YAML (analysis only).
  - The CD half: image push to ghcr and `update-deployment-tag` (`.tekton/push.yaml` tail) — "ci works" is read as build/test/image-build only (see Open Questions).
  - Changes to `infra/pac/`, the GitHub App, or the deploy repo.
  - Changing the application source or `pom.xml`.

## Implementation

### Target flow
```
PipelineRun (tekton_ci/pipelinerun.yaml)
  workspaces:
    build-mem  -> emptyDir { medium: Memory, sizeLimit: 2Gi }      # task-local, task 1 only
    shared     -> volumeClaimTemplate (RWO, 1Gi, local-path)       # ONE PVC per run, bound to every task
  pipelineRef  -> Pipeline (tekton_ci/pipeline.yaml)

Pipeline
  workspaces: [build-mem, shared]
  task 1: clone-build-memory   (custom Task, ONE pod)
            workspaces: build-mem -> build-mem, output -> shared
            step clone : git clone <repo_url>@<revision> into build-mem
            step build : mvn package in build-mem          # the ONLY Maven build in the flow
            step copy  : copy target/<jar> + Dockerfile -> shared (PVC), same relative paths
  task 2: buildah (Hub), runAfter task 1
            workspaces: source -> shared (same PVC)
            context = PVC root: Dockerfile + target/<jar>   # no source, no mvn in the image build
            SKIP_PUSH=true
```

### PVC workspace is the cross-task shared volume
- The PVC is declared **once**, as a Pipeline-level workspace (`shared`), and bound by the PipelineRun with a `volumeClaimTemplate`. Tekton creates one PVC per PipelineRun and mounts that same claim into every task that references the workspace — this is exactly how `source` works in `.tekton/pr.yaml` / `push.yaml` (bound to `fetch-source`, `maven-test`/`maven-package`, `build-image`).
- Every Pipeline task that needs data from another task gets it from `shared`; no task-to-task data moves through `build-mem`. Any task added later (e.g. a scan or a push step) binds `shared`, not a new volume.
- Each task maps the pipeline workspace onto its own declared workspace name (`output` in the custom Task, `source` in Hub `buildah`); the names differ, the underlying PVC is the same.
- Sharing is **sequential, not concurrent**: the claim is RWO, so tasks using it must be ordered with `runAfter` (or an implicit result dependency). `coschedule: workspaces` (affinity assistant) pins all pods of the run that use the PVC to one node, which is what makes RWO sharing work on `local-path`.
- Lifetime: the PVC is owned by the PipelineRun and is deleted with it — shared between tasks of one run, never between runs.

### Why clone and build must be one Task
An `emptyDir` workspace is per-pod. Each Tekton `TaskRun` is its own pod, so an `emptyDir` bound at the PipelineRun level gives every task a *different, empty* volume — nothing is shared between tasks. The reference design (Hub `git-clone` task, then Hub `maven` task) therefore cannot be kept as-is with a memory workspace: the clone would vanish before Maven runs. The clone and the Maven build must be **steps of a single custom Task**, and the copy to the PVC must be the last step of that same Task. This is why the request needs a new Task rather than just a new Pipeline wiring Hub tasks.

Consequence: Hub `git-clone` and `maven` are no longer used by the new pipeline; their behaviour (checkout of an exact revision, `settings.xml` handling, goals param) has to be reproduced in the custom Task's steps to the extent needed. `buildah` stays a Hub task because it runs after the hand-off, on the shared PVC.

### Memory workspace
- Bound in the PipelineRun as `emptyDir: {medium: Memory, sizeLimit: 2Gi}`; the Task only declares a workspace and is unaware of the medium. (Alternative: declare the tmpfs as a Task-level `volume`, which makes the Task self-contained but is no longer a "workspace".)
- tmpfs pages are charged to container memory. Everything written to the workspace (clone, `target/`, and the Maven local repository if it is placed there) competes with the JVM heap for the same memory budget.

### "memory limit = 2G"
Two distinct knobs exist and the request does not say which:
1. **tmpfs size** — `emptyDir.sizeLimit: 2Gi`. Exceeding it yields `ENOSPC` / pod eviction.
2. **container memory limit** — `computeResources.limits.memory: 2Gi` on the Task's steps. Exceeding it yields an OOMKill.

Step-level `computeResources` in the Task spec is a stable field and works on the cluster as-is. The PipelineRun-side override `taskRunSpecs[].computeResources` (task-level) is an alpha feature and the cluster runs `enable-api-fields: beta`, so the limit should live in the Task (or in `taskRunSpecs[].stepSpecs`).

Sizing reality for this app: source is a few KB, `target/` tens of MB, the Spring Boot dependency set in `~/.m2` is roughly 150–250 MB. 2Gi is comfortable for either interpretation, provided the JVM heap is not left to grow unbounded against a limit that tmpfs also draws on.

### Dockerfile: build stage removed
- The `build` stage (`FROM …/openjdk-17 AS build`, `COPY pom.xml`/`src`, `RUN mvn -B -DskipTests package`) is deleted. What remains is the runtime stage on `ubi9/openjdk-17-runtime`, with `COPY --from=build /build/target/demo-0.0.1-SNAPSHOT.jar app.jar` replaced by a `COPY` of the jar **from the build context** (`target/demo-0.0.1-SNAPSHOT.jar`).
- The image build no longer compiles anything, needs no JDK/Maven image and no network access to Maven Central. The jar that was tested by the Tekton Task is the exact jar that ships in the image — the previous "build twice" redundancy is gone.
- The jar path stays coupled to `pom.xml` (`artifactId` + `version`): the same literal filename is still hard-coded in `Dockerfile`, as it is today.

### What gets copied to the PVC
Only what `buildah` needs as its build context:
- `target/demo-0.0.1-SNAPSHOT.jar` — the build result.
- `Dockerfile` — "just the jar" is not literally sufficient, because `buildah` reads the Dockerfile from its `source` workspace (default `DOCKERFILE=./Dockerfile`, `CONTEXT=.`).

Both are placed at the same relative paths as in the repo, so the Hub `buildah` task runs with its default params and the same `Dockerfile` works for local `docker build`. Source, `pom.xml`, `.git` and the rest of `target/` never leave the memory workspace.

Spring Boot leaves a second file, `target/demo-0.0.1-SNAPSHOT.jar.original` (the non-executable thin jar); the copy must select the repackaged jar by exact name, not by `*.jar*` glob.

### Maven build happens only in the Tekton Task
- The build step must run a goal that produces the jar: `package` (or `verify`). `test` — what the reference `pr.yaml` runs — produces no jar and is no longer sufficient.
- Tests run as part of `package` in the Task (the old Dockerfile used `-DskipTests`), so the Task is both the test gate and the artifact producer.

### Impact of the Dockerfile change on existing consumers
`Dockerfile` is shared, so removing its build stage reaches beyond `tekton_ci/`:

| Consumer | Today | After the change |
|---|---|---|
| `.tekton/push.yaml` | `maven` `package` on the PVC, then `buildah` rebuilds inside the Dockerfile | Still works: `target/<jar>` is already on the `source` PVC when `buildah` runs. Becomes single-build |
| `.tekton/pr.yaml` | `maven` `test`, then `buildah` builds via the Dockerfile's own Maven stage | **Breaks**: `test` leaves no jar, so the `COPY` fails in `build-image`. Needs `GOALS: ["package"]` to keep working |
| Local `docker build -t demo-app .` | Self-contained | Requires `mvn package` first; without `target/<jar>` the build fails |
| `CLAUDE.md` Commands | "`Dockerfile` does this too" | Stale; the note and the local build instructions must change |

Because of `pipelinerun_provenance: default_branch`, the `Dockerfile` (taken from the PR head) and `.tekton/pr.yaml` (taken from `main`) change at different moments: a PR that changes both still runs the *old* `pr.yaml` (`test`) against the *new* Dockerfile and fails at `build-image`. The `pr.yaml` goal change has to reach `main` before, or independently of, the Dockerfile change.

### Relationship to PAC
PAC discovers pipeline definitions only under `.tekton/`. Files in `tekton_ci/` are therefore plain Tekton resources:
- **Standalone use**: `kubectl apply` the Task and Pipeline into `cicd-demo`, `kubectl create` the PipelineRun (needs `generateName`, and concrete `repo_url` / `revision` values — PAC's `{{ repo_url }}`, `{{ revision }}`, `{{ pull_request_number }}` are not substituted outside PAC).
- **PAC-triggered use**: a PipelineRun under `.tekton/` must exist and pull the others in via annotations (`pipelinesascode.tekton.dev/pipeline: "tekton_ci/pipeline.yaml"`, `.../task: "[tekton_ci/task.yaml, buildah]"`). Repo-relative paths in these annotations are already used by `push.yaml` (`task-1: "[.tekton/tasks/update-deployment-tag.yaml]"`).

In the PAC case, if the new PipelineRun matches `pull_request`→`main` while `.tekton/pr.yaml` remains, **both** run on every PR.

## Constraints & Edge Cases
- **emptyDir is not shared across tasks** — the single-Task design is mandatory, not stylistic. Conversely, the PVC is the *only* thing shared across tasks; anything not copied to it by the end of task 1 is gone.
- **Shared PVC is RWO**: tasks bound to it cannot run in parallel on different nodes; ordering via `runAfter` is required, and the affinity assistant keeps them co-located. A failed copy step leaves the PVC empty or partial, so task 1 must fail (non-zero exit) rather than let `buildah` start on incomplete content.
- **Shared PVC starts empty and is written once**: only task 1 writes the tree; `buildah` reads it (and writes its own build layers elsewhere). If more writers are added later, use `subPath` on the workspace binding to keep them from clobbering each other.
- **tmpfs counts as memory**: with a 2Gi container limit and a 2Gi tmpfs cap, filling the tmpfs OOM-kills the step before `sizeLimit` triggers. Heap should be bounded explicitly (e.g. `MAVEN_OPTS`), and the location of the Maven local repo (tmpfs vs. container filesystem) is a memory-budget decision.
- **Every step container in the pod carries its own limit**; a per-step 2Gi limit on three steps makes the pod's total limit 6Gi even though steps run sequentially. The "2G" intent may be per step or per pod.
- **Units**: `2G` (10⁹) vs `2Gi` (2³⁰) — Kubernetes accepts both; reference files use `Gi`.
- **No dependency cache**: tmpfs and per-run PVC are both discarded, so every run re-downloads all Maven dependencies (same as the reference today) — but now once per run instead of twice.
- **File ownership on the PVC**: the copy step and `buildah` may run as different UIDs; the copied jar and `Dockerfile` must be readable by `buildah`.
- **No jar, no image**: with a runtime-only Dockerfile any pipeline whose Maven goal stops before `package` fails at the image build, not at the Maven step — the error surfaces one task later than its cause.
- **`target/` is git-ignored but not docker-ignored**: there is no `.dockerignore`, so the jar under `target/` is visible to the build context — required for the new `COPY`. Adding a `.dockerignore` that excludes `target/` later would break the image build.
- **One PVC only**: with `coschedule: workspaces` a TaskRun may bind at most one PVC-backed workspace — satisfied here (one tmpfs + one shared PVC). This also rules out a design with separate per-task PVCs chained together; a single shared claim is the only option under the current cluster config.
- **Checkout must pin the revision** (`git checkout <sha>`), not just clone the default branch, to match Hub `git-clone` semantics.
- **Private repo**: the reference clones without credentials (public repo). If that changes, the custom Task needs the `{{ git_auth_secret }}` via a workspace, never via `env` (CLAUDE.md gotcha).
- **Provenance**: any `.tekton/` entry point for the new pipeline only takes effect after merge to `main`; pre-merge validation must use `tkn pac resolve` / direct `kubectl create`.
- No `LimitRange` or `ResourceQuota` exists in `cicd-demo`, so nothing else injects or caps memory.
